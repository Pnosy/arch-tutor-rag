# Arch-Tutor 设计与实施文档

> 交付物附册：技术选型理由、系统架构、关键设计决策

## 一、技术选型

### 1.1 选定方案：方案 C（从零搭建）

| 层次 | 选型 | 说明 |
|---|---|---|
| 知识库 | SQLite + FTS5（trigram 分词） | 单文件、零服务、无需额外依赖 |
| 排序 | BM25（FTS5 内置 `bm25()`） | 成熟的相关度算法 |
| 智能体 | 直接调用 LLM API + 自定义检索逻辑 | 理解最深入，无框架黑盒 |
| 提示词 | 五段式系统提示词 | 逐段对应 R1~R6 |

### 1.2 为什么选方案 C 而非 A/B/D

- **对比方案 A（DSH + 自定义插件）**：方案 A 是教师参考路径。作业明确
  「选择非参考路径且实现完整者，技术选型项可获满分」。方案 C 的检索链
  完全自研，更能体现对 RAG 原理的理解。同时我们**额外提供了 DSH 插件实现**
  （`agents/arch-tutor-plugin.js`），因此并不放弃方案 A 的生态兼容性。
- **对比方案 B（LangChain / LlamaIndex）**：向量检索需引入 embedding 模型与
  向量库，依赖重、环节多；对于「中文教材 + 精确术语检索」这一场景，
  FTS5+BM25 的确定性更好、可解释性更强，且便于逐条验证 R1~R6。
- **对比方案 D（低代码平台）**：平台封装了检索过程，无法深入控制
  「先检索后回答」的执行顺序，不利于 R1 的强制与取证。

### 1.3 技术栈对比实验（拓展挑战）

我们实际做了 FTS5 与「关键词 LIKE 匹配」的对照，说明分词器选择的影响：

| 检索方式 | 中文查询「直接相联组相联」Top-1 | 说明 |
|---|---|---|
| 无索引 `LIKE '%词%'` | 命中但无排序 | 只能返回布尔结果，无法按相关度排序 |
| FTS5 `unicode61` | 0 命中 | 中文整句被当作单一 token，无法切分 |
| **FTS5 `trigram`** | **命中 p.280（正确）** | 3 字符滑窗，中文子串匹配良好 |

结论：**中文教材必须使用 trigram（或专门的中文分词器）**，`unicode61`
在中文场景下几乎不可用。

## 三、Phase 1 关键设计决策

### 3.1 章节边界检测：用 PDF 书签而非正则

教材 PDF 由 LaTeX(hyperref) 生成，自带 **210 条书签**，层级清晰：

```
level 1 -> 部分 (6 个：第一部分 引言 ... 第六部分 系统性能评价与分析)
level 2 -> 章   (12 个：引言 / 指令系统 / 特权指令系统 / ... )
level 3 -> 节   (72 个)
level 4 -> 小节 (120 个)
```

**决策**：直接读取书签构建章节树，以 level≤2 作为「章」边界。

**理由**：正则匹配「第 X 章」在中文 PDF 中易受页眉、目录页、交叉引用干扰；
书签是出版方的权威结构信息，零误判。实测 12 章边界与目录完全一致。

### 3.2 分块策略：结构优先 + 双硬约束

| 参数 | 取值 | 依据 |
|---|---|---|
| TARGET_TOKENS | 1000 | 作业要求 800~1200 的中值 |
| MIN_TOKENS | 800 | 作业要求下限 |
| MAX_TOKENS | 1200 | 作业要求上限 |
| OVERLAP_CHARS | 180 | 防止答案被块边界切断 |
| SPLIT_TOLERANCE | 1.12 | 容忍轻微超限，避免「1201 → 600+600」的劣化切分 |

**分块算法**（章内）：

1. 按段落/句聚合为单元序列；
2. 逐单元累加，遇到以下任一情况断开：
   - **硬约束**：加入该单元会超过 `MAX - safety`（safety 为重叠量的一半）
   - **软偏好**：该页是小节起点，且缓冲已达 `TARGET × 0.85`
3. 断块后把尾部 180 字符作为下一块开头（块间重叠）；
4. 章末残余优先并入上一块，若合并会超上限则单独成块
   （小结/习题是自然语义边界，允许略小于 800）。

**踩过的坑（重要）**：早期版本在 `flush()` 中做「超限即二分」，
导致 1201 token 的块被切成两个 600 token 的**半满块**，一次产生 50 对
劣质块。修正方式是引入 `SPLIT_TOLERANCE`：仅当超过 `MAX × 1.12`
才真正切分，且切分后若出现过小片段则回退为不切分。

**最终效果**：

| 指标 | 数值 |
|---|---|
| 总块数 | 277 |
| token 均值 | 1082.5 |
| token 范围 | 344 ~ 1199 |
| 落在 800~1200 | **270 块（97.5%）** |
| 超过 1200 上限 | **0 块** |
| 低于 800 | 7 块（全部为章末块） |

### 3.3 中文检索：trigram 分词器

**问题**：FTS5 默认 `unicode61` 按空白与标点切词，中文没有空格，
整句会被视为一个 token，导致查询「Cache」以外的中文词全部 0 命中。

**决策**：使用 `tokenize='trigram'`，把文本切成 3 字符滑窗。

**代价与应对**：trigram 要求查询词 ≥3 字符，2 字词（如「异常」「方式」）
无法直接命中。应对措施：

1. `build_match_expr()` 只生成 ≥3 字符的 MATCH 词；
2. `_probe_terms()` 同样过滤 <3 字符的词——否则这些**永远无法命中**的词
   会计入覆盖度分母，系统性拉低所有候选得分、破坏排序区分度（实测踩坑）；
3. 通过同义词表把 2 字查询映射到更长的教材术语。

## 四、Phase 2 关键设计决策

### 4.1 为什么提示词之外还要加「机制」

纯提示词约束存在被模型绕过的风险。因此对最关键的 R1 采取**双保险**：

1. **提示词层**：第 4 条把「调用 knowledge_search」定义为回答的前置条件；
2. **代码层**：`arch_tutor_agent.run()` 中，检索是回答函数调用链的
   **必经步骤**——`answer_offline` / `answer_with_api` 都接收
   `hits` 参数，没有检索结果就无法进入事实生成分支。

这样即使模型「想」跳过检索，运行时也不存在绕过路径。

### 4.2 相关性闸门：解决 R2/R5 的隐性违规

**发现的问题**：冒烟测试 T5（「帮我写 Java 冒泡排序」）时，
FTS5 因「指令」「程序」等词命中了教材中的无关片段（5 条），
离线智能体便据此作答 —— 这**违反了 R2/R5**（用无关内容充当依据）。

**根因**：FTS 的「有命中」不等于「相关」。trigram 的 OR 召回策略
天然会引入噪声。

**解法**：新增 `relevance_gate()`，用**实义关键词覆盖率**判定：

```
覆盖率 = (问题中能在命中片段里找到的词数) / (问题实义词总数)
覆盖率 >= 0.34  -> 通过
```

未通过则视为「教材未覆盖」，走 R5 的诚实回答分支。

**效果**：T4（量子纠缠）与 T5（Java 代码）均被正确拦截，
R2/R5 通过率从 80% 提升到 100%。

### 4.3 二次排序：为什么不能只靠 BM25

单纯 `ORDER BY bm25() LIMIT 3` 时，查询「指令流水线的基本原理」
返回的是 p.164、p.421、p.147，**完全没命中真正的「指令流水线」章节**。

**根因**：SQL 直接 `LIMIT topk(=3)`，重排只能在 3 条候选里打转，
真正相关的块根本没进入候选集。

**解法**（两处改动）：

1. **扩大候选池**：`LIMIT max(topk×8, 40)`，先召回再精排；
2. **合成打分**：
   ```
   final = 0.35×词覆盖度 + 0.15×完整短语命中
         + 0.30×章节/小节标题命中 + 0.20×BM25相对排名
   ```
   其中 BM25 用**相对排名**而非绝对值——本库 BM25 分数集中在 -3~-7，
   直接归一化会全部饱和、失去区分度（实测踩坑）。

**效果**：「指令流水线的基本原理」Top-1 从 p.164 修正为
p.281（小结）、p.265（指令相关和流水线冲突）等真正相关章节。

### 4.4 同义词扩展：解决「用户用词 ≠ 教材用词」

用户问「Cache 的**映象**方式」，而教材用的是「**相联**」（直接相联/全相联/组相联）。

**验证过程**：先确认教材确实覆盖该内容——

```
教材含 '映象': 0 块      <- 用户用词
教材含 '映像': 2 块
教材含 '直接相联': 3 块   <- 教材实际用词
教材含 '组相联': 5 块
```

**解法**：内置体系结构术语同义词表 `SYNONYMS`（映象↔映像↔映射↔相联、
Cache↔高速缓存、TLB↔快表 等），在查询预处理阶段扩展。

**效果**：该查询现正确返回 p.279-280（直接相联/全相联/组相联的讲解）。

### 4.5 检索质量最终指标

| 指标 | 数值 |
|---|---|
| Top-1 准确率 | 8/10 = **80%** |
| Top-3 命中率 | 9/10 = **90%** |
